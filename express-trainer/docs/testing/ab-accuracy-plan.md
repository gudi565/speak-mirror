# M0 · 新旧识别引擎准确率 A/B 对比方案

- 背景：M0 把识别链路从 `sherpa-rs`（停维护）+ 流式 Zipformer 迁移到官方 `sherpa-onnx` crate + 流式 Paraformer 中英双语 int8（产品方案 §5.1）。
- 目的：用同一段真实口播素材，客观回答"新引擎是否**肉眼可见地**更准"，为迁移决策提供依据；素材与数据同时留档，作为后续模型升级（如 SenseVoice 二次识别）的基线。
- 结论先行：**新引擎三段素材的字错率全部下降、且平均相对降幅 ≥ 25%，同时无一段句级劣化，才算迁移成功；否则钉住旧引擎排查配置。**

## 1. 测试素材（3 段 × 约 3 分钟，一次录制全程复用）

| 素材 | 时长 | 内容要求 | 难度针对性 |
|---|---|---|---|
| A · 正常语速 | ≈3 min | 事先写好约 800–900 字底稿（话题任选，如自我介绍/项目讲解），照稿自然讲述，语速 220–260 字/分 | 基线准确率 |
| B · 快语速 | ≈3 min | 同一人刻意加速到 300 字/分以上，允许吞字与含糊 | 流式模型在高速音流下的稳定性与 VAD 断句 |
| C · 口头禅密集 | ≈3 min | 不写稿、自然即兴聊天式讲述，鼓励"然后/就是/那个/呃"高频出现，可夹杂停顿、改口、半截句 | 高频短填充词的识别与断句（M2 规则引擎直接受益） |

录制纪律：

- 同一环境（安静室内、无键盘/风扇噪声）、同一设备、麦克风距离固定（20–30 cm），一次 session 内录完三段。
- 48 kHz 或 44.1 kHz 录制均可，统一转 16 kHz 单声道 WAV 后再喂引擎（两条链路输入必须逐字节相同）。
- **不要**对着两个引擎分别实时说话——必须"录一次、回放两次"，否则变量不唯一。

## 2. 参考答案（Ground Truth）制作

- 素材 A/B：以底稿为初稿，逐句听音核对，把实际讲述与底稿不一致处（跳句、换词、口误）**改成实际说出的内容**——参考答案必须忠于音频而不是忠于稿子。
- 素材 C：无底稿，逐句人工转写（听两遍：第一遍转写、第二遍校对）。
- 参考答案按"句"组织（每句一行），保留口头禅与语气词，**不做任何书面化修饰**。
- 规范化口径（计算前对两边统一执行）：去掉标点与空格；数字按读音归一（"2005 年"与"二零零五年"统一为一种写法）；英文统一小写。

## 3. 对比层级与指标

### 3.1 字级（主指标）

- 字错率 `CER = (S + D + I) / N`，N 为参考答案总字数，S/D/I 为相对参考答案的替换/删除/插入数，用编辑距离计算（Python 可用 `jiwer` 或 `rapidfuzz.distance.Levenshtein`）。
- 每段素材分别算 CER，不做三段混合（快语速与正常语速的难度不同，混在一起会掩盖单段劣化）。

### 3.2 句级（辅指标，产品方案 §5.1 的验收口径）

- **句级错字率** = 含至少 1 个错字的句子数 / 总句数。这是"肉眼可见"的直接度量：把每个终稿句与参考句并排打印，错字句一眼可数。
- 句子对齐：按时间戳贪心对齐（终稿句与参考句取重叠时间最大者），对不齐的句计为整句错误。快语速下两引擎 VAD 断句差异大，句子数可能不同——这正是要观察的现象，不影响"含错句比例"的可比性。

### 3.3 资源与体验（不达标同样打回）

- CPU 峰值占用（任务管理器/`typeperf` 采样）、内存增量、首字延迟、600ms partial 节流下的字幕跟手程度（主观）、实时率 RTF < 1。

## 4. 操作步骤

1. 按第 1 节录制三段素材，转 16 kHz 单声道 WAV，存 `docs/testing/fixtures/`（文件大则本地留存不进 git，登记哈希即可）。
2. 按第 2 节制作参考答案 `fixtures/{A,B,C}.ref.txt`（每句一行）。
3. 旧引擎跑一遍：同一 WAV 文件以文件回放方式喂入现行链路，**只收终稿句**（忽略 partial），导出 `fixtures/{A,B,C}.old.txt`（每句一行，附时间戳）。
4. 新引擎跑一遍：同口径导出 `.new.txt`。两引擎标点策略保持一致（都开或都关，建议都开，计算前规范化时统一去除）。
5. 计算字级与句级指标（脚本要点见附录），填入第 5 节表格。
6. 人工抽查：每段随机抽 10 句，打印"参考 / 旧引擎 / 新引擎"三栏对照，肉眼确认指标方向与观感一致（防止对齐 bug 制造虚假收益）。
7. 按第 6 节判定标准给出迁移结论，表格与本文件一起归档。

## 6. 判定标准（迁移门槛）

**迁移成功**（同时满足）：

1. 字级：三段素材新引擎 CER 全部 ≤ 旧引擎，且平均相对降幅 ≥ 25%（对应产品方案"错字肉眼可见减少"的量化口径）。
2. 句级：三段合计"含错句比例"下降，且 4.6 步人工抽查方向一致。
3. 资源：CPU 峰值不高于现状 +10%，RTF < 1。

**任一条件触发即打回排查**（不达标 ≠ 换模型解决，先查配置）：

- 任一段 CER 不降反升超过 5%（绝对）；
- 句级含错句比例上升；
- CPU 明显劣化。

常见排查项：采样率/声道不一致、标点恢复开关不一致、流式分块尺寸、VAD 灵敏度、模型是否 int8 正确加载、回放音量削波。兜底（产品方案 §5.1）：官方 crate 在 Windows 构建受阻时短期钉住 sherpa-rs，M1 不被阻塞。

## 7. 留档与复用

- 本方案产出的素材与参考答案是资产：Paraformer 不达标时，SenseVoice 二次识别的 A/B 用同一套素材直接重跑；M3 声音层指标的回归测试也可复用三段录音。
- 表格填完后随 `docs/testing/` 提交；素材 WAV 本体按仓库策略决定是否入库（建议 ≤10MB 可入，否则登记哈希本地保存）。

## 附录 · CER 计算脚本要点（Python）

```python
# pip install jiwer
from jiwer import cer  # 或用 rapidfuzz 自算编辑距离
import json

def norm(t: str) -> str:
    # 去标点、去空白；如素材含数字读法差异，先做统一替换
    return "".join(c for c in t if c not in "，。！？、；：…—,.!?;: \t")

ref = open("fixtures/A.ref.txt", encoding="utf-8").read()
old = open("fixtures/A.old.txt", encoding="utf-8").read()
new = open("fixtures/A.new.txt", encoding="utf-8").read()
print("old CER:", cer(norm(ref), norm(old)))
print("new CER:", cer(norm(ref), norm(new)))

# 句级：按行 zip 后逐句比较 norm 后是否相等，统计含错句比例
```

注意：`jiwer.cer` 返回的是错误率（0–1），乘 100 得百分数；若参考与识别句数不一致，先按时间戳对齐再逐句比。
